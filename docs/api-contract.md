## 1. Response envelope

Every service module (all except `api-gateway`) returns `ResponseErrorTemplate`:

```java
// common/src/main/java/com/ticket/common/exception/ResponseErrorTemplate.java
public record ResponseErrorTemplate(
    String message,   // human readable
    String code,      // ApiConstant key, e.g. "200", "EVT_NOT_FOUND"
    Object data,      // payload, or null
    boolean is_error  // true => failure
) {}
```

Wire shape:

```json
{
  "message": "Event retrieved successfully",
  "code": "200",
  "data": { "id": 1, "title": "..." },
  "is_error": false
}
```

The same envelope is used for both success and failure — the HTTP status is
**not** the carrier of error state. `api-gateway` uses an incompatible
envelope and is the sole exception:

```json
{ "success": true, "errorCode": "200", "message": "Request was Success", "data": {} }
```

The dashboard parses `is_error` (see `frontend-admindashboard/src/lib/api.ts`),
so it works against services and silently breaks against the gateway.

## 2. Authentication

`Authorization: Bearer <accessToken>`. Issued by `POST /api/v1/auth/login`.

Only `user-service` and `api-gateway` declare `spring-boot-starter-security`.
`CustomSecurityFilterChain` (user-service) is the single authorization point:

| Path pattern | Rule |
|---|---|
| `/api/v1/auth/**`, `/api/public/**`, `/health`, `/actuator/**`, `/swagger-ui/**`, `/v3/api-docs/**` | `permitAll` |
| `/api/v1/users/**`, `/api/v1/roles/**`, `/api/v1/groups/**`, `/api/v1/permissions/**` | `hasAnyAuthority("USER","ADMIN")` |
| `/api/admin/**` | `hasAuthority("ADMIN")` |
| any other request | `authenticated` |

Roles are `ADMIN`, `USER`. **`MANAGER`, `AGENT` and `VIEWER` do not exist in the
backend** — the plan's Phase 5 RBAC tests reference them.

## 4. Pagination

Only `user-service` (users, roles, groups, permissions) paginates, via
`PageableRequestVO` (`pageNumber` 0-based, `pageSize`, `sortBy`, `desc`) and
`PageableResponseVO`:

```json
{
  "totalElements": 42, "content": [], "pageNumber": 0, "pageSize": 10,
  "totalPages": 5, "first": true, "last": false, "empty": false,
  "metadata": { "hasNext": true, "totalUsers": 42, "hasPrevious": false,
                "currentPage": 0, "pageSize": 10 }
}
```

Wrapped inside the envelope, so `data.content` holds the rows.

`event`, `ticket`, `order`, `payment` and `notification` list endpoints return
**unpaginated arrays**.

## 5. Known deviations

These are the contract's actual defects, in severity order.

### D1 — Errors are returned with HTTP 200
Only `user-service/GlobalExceptionHandler` (400/409/500) and
`PublicController.verifyToken` (401) set real statuses. Every other service
returns `ResponseEntity.ok(...)` for all outcomes. A missing event is
`HTTP 200` + `is_error: true`. Consequences: caches and CDNs treat failures as
success, monitoring cannot count errors, and any client that keys on status
code silently mis-handles failures. The plan's 400/401/403/404/409/422
requirement is unmet across 5 of 7 modules.

### D2 — Admin endpoints are unprotected outside user-service
`event`, `ticket`, `order`, `payment` and `notification` have **no
`spring-boot-starter-security` at all**. Under the microservice topology every
`/api/admin/**` route in those services is reachable unauthenticated. Safety
depends entirely on `api-gateway` being the only ingress.

### D3 — Notification admin surface escapes the ADMIN rule
`AdminNotificationController` is mapped to `/api/v1/notifications`, so it does
not match the `/api/admin/**` → `hasAuthority("ADMIN")` rule. `POST /{id}/resend`
and `DELETE /{id}` are available to any authenticated `USER`.

### D4 — Pagination envelope does not match the client
Backend: `content` / `totalElements` / `pageNumber` / `pageSize`.
Dashboard `PaginatedResponse<T>`: `data` / `meta.total` / `meta.page` / `meta.limit`.
None of the paginated fields line up, so `data?.data` and `data?.meta?.totalPages`
both resolve to `undefined` and pagination renders as a single page.

### D5 — Path-variable shadowing: checked, not a problem
`GET /{id}` coexists with `GET /stats` on events, tickets, orders, payments and
notifications, which looks like it should break `Long` conversion. Verified
against the running monolith: `GET /api/v1/events/stats` returns the stats
payload, because Spring's literal-path patterns take precedence over `{id}`.
No action needed.

### D6 — Two envelopes
Services use `{message, code, data, is_error}`; the gateway uses
`{success, errorCode, message, data}`.

| Called by | Path | Backend status |

## 7. Not implemented at all

- **Kafka.** Zero `KafkaTemplate`, zero `@KafkaListener`. The producer call in
  `OrderServiceImpl` is commented out and references a class that does not
  exist; `NotificationServiceImpl.handlerOrderConfirmationEvent` has no caller.
  `spring-kafka` is declared in `payment-service`, which has no Kafka code.
- **Roles `MANAGER` / `AGENT` / `VIEWER`.**
- **Idempotency keys** for checkout or payment callbacks.
- **Reservation expiry** / release on payment failure or order timeout.
- **Password reset by email** (admin-triggered reset only).
- **Push notifications** (`PUSH_NOTIFICATION` enum value, no implementation).
- **Refresh-token rotation on reuse detection.**
